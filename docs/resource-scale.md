# 资源雷达规模化策略

资源雷达的近期目标是支撑 `1000-3000` 条本地资源，而不是十万级资料库。当前阶段继续使用本地 JSON，优先通过前端索引和虚拟列表解决真实瓶颈。

## 当前选择

- 数据文件仍是 `%APPDATA%/local-dev-cockpit/skill-radar.json`。
- `/api/skills` 默认保持兼容，返回完整资源列表。
- `/api/skills?summary=1` 返回轻量摘要：总数、状态统计、类型统计、大类/小类统计和最近更新时间。
- 前端进入资源页后构建 `ResourceIndexEntry`，预计算搜索文本、大类、小类、状态、类型和来源域名。
- 列表采用固定行高虚拟滚动，只渲染可视区域和少量缓冲项。
- 星云图根据资源数量自动降级，避免在大数据下渲染上千个 Three.js 节点。

## 星云图降级规则

- `<= 120` 条：显示完整资源节点。
- `121-1000` 条：显示分类星团和代表资源；点击分类后只展开该分类节点。
- `> 1000` 条：默认只显示分类星团和数量，不渲染所有资源卡节点。

星云图仍然按需动态加载 Three.js，离开视图后释放 renderer、scene、geometry、material 和动画帧。

## 导入去重规则

导入资源包时会返回新增、跳过和失败数量。去重规则按顺序覆盖：

- `id`
- 标准化后的来源 URL
- GitHub `owner/repo`
- 标题 + 摘要指纹

坏数据不会中断整批导入，会计入 `failed`。

## 何时再引入数据库

暂不引入 SQLite 或全文检索库。触发重新评估的条件：

- 单机资源超过 `5000` 条。
- 需要全文检索排序、模糊搜索、相似资源聚类。
- 导入导出开始出现明显 JSON 读写延迟。
- 需要按时间线、来源、标签做复杂组合查询。

在这些条件出现前，JSON + atomic write + 前端索引更简单，维护成本更低。
